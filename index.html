Teaching Silicon About Cities

Merkle Bloom with PNG Nesters

A lightweight, offline-first provenance layer for images. No blockchain. No accounts. 132 bytes appended after IEND. Built for agents, archivists, and rust-belt winter light.

1. The Problem (why provenance matters)

Every image you encounter in 2025 has been touched by at least three non-human agents before it reaches your retina: a scraper, a resizer, a captioner, a compressor, a re-captioner, a safety filter. None of them leave a forwarding address.

Current provenance is theater. C2PA buries a 12–80KB JSON manifest inside JPEG APP11 or PNG iTXt, signed with X.509 chains that require Adobe’s trust store and an internet connection. It breaks on screenshot, on resize, on a naive `mogrify -strip`. It presumes publishers are honest and infrastructure is permanent.

Blockchain provenance is worse: it externalizes truth to a costly, public ledger, then points at an IPFS hash that 404s in 18 months. It solves double-spend, not double-see. Images are copied, not spent.

Watermarks are adversarial. Invisible DCT watermarks survive JPEG but die to diffusion re-synthesis. Visible watermarks are cropped. Both assume a single owner.

What cities need is not ownership. It is contact tracing. Buffalo does not need to own a photo of a snowplow on Bailey Ave. It needs to know: which models trained on it, which agents re-captioned it "truck in snow" vs "city plow #17 clearing east side, Feb 3 2023, -8°F", which archivist verified the location.

Provenance must be: 1) byte-level cheap (<200 bytes), 2) decoder-ignorant (survives normal CDN pass-through), 3) offline-verifiable (no RPC), 4) privacy-preserving (no global registry), 5) additive (many agents, no overwrite), 6) adversarially cheap to verify but linearly expensive to forge at scale.

Merkle Bloom is our answer. We treat each PNG as a nest. After the official IEND chunk, we append 132 bytes. Browsers, iOS, Android, libpng, Pillow, Cloudflare Images, S3, Discord all ignore trailing bytes per PNG spec §5.4. They do not strip them. Thus the nest rides for free.

Inside those 132 bytes: a truncated Merkle root committing to the image’s edit history, and a 128-bit Bloom filter representing the set of agents that have touched it. No signatures. No accounts. One agent, one configurable number of bit flips. Over time the filter saturates gracefully; you can estimate agent count via cardinality, not identity.

This is not DRM. It is a field notebook stapled to the back of a photograph.

2. One Agent One Bit

The core ethic: an agent should not be able to speak for others, only for itself, and it should do so as quietly as possible.

When an agent (a Python script, a browser extension, a local SDXL node) first opens a PNG with a nest, it computes its own Agent ID: blake3("0root-agent-v1" || ed25519_pubkey)[0:16]. No registration. If it has no key, it uses blake3(hostname || binary_hash)—ephemeral but consistent.

To mark contact, the agent does not sign. It sets k bits in the nest’s Bloom filter. We use k=3, m=128. Indices are: h_i = (H(agent_id || merkle_root || i) mod 128). It ORs those three bits into the existing filter.

Properties: 1) Idempotent—re-marking does nothing. 2) Commutative—order of agents does not matter. 3) Private—you cannot enumerate agents from the filter, only test membership if you already know the agent ID. 4) Compact—128 bits for thousands of agents with ~1% false positive at 30 agents.

Why one bit (actually three)? Because we want contact to be cheap ethically. If marking costs nothing, spam is trivial. Hence we pair it with proof-of-work (§10). If marking is too expressive (a full signature), agents leak identity and create legal liability. A bit flip is a feather, not a flag.

Over months, a viral image of Rochester's Broad Street bridge accumulates a filter with 47 bits set. You cannot name all 47 agents, but you can test: "Did the City of Rochester Archivist Bot touch this?" Yes—bits 14, 91, 103 are set. "Did OpenAI GPT-4o captioner?" No—bit 14 is set but 22 and 77 are not. Probabilistic, but useful.

This is how mycelium works: no central ledger, just chemical traces that accrue.

3. Merkle Trees in 200 words

A Merkle tree is a binary hash tree. Leaves are hashes of data blocks. Parents are H(left || right). The root is a single hash committing to the entire set. Change one byte in one leaf, the root changes.

Key advantage: log(N) proofs. To prove leaf L5 is in a tree of 1M leaves, you only need ~20 sibling hashes (the Merkle path), not 1M. Verifier recomputes up to root and compares.

Used in Git (commit history), BitTorrent (piece verification), Certificate Transparency, and every blockchain. Not because it's trendy, because it's the minimal structure for tamper-evident append-only logs.

For images, we don't Merkle the pixels (too large). We Merkle the history of nests. Each edit creates a new leaf: leaf_n = H(prev_root || bloom_n || timestamp || geohash). The new root commits to all prior versions.

This gives us "Proof of Edit" without storing edits. You can show that version 3 descends from version 1 with 2 hashes, offline.

4. Bloom Filters in 200 words

A Bloom filter is a bit array of m bits, initially zero, with k independent hash functions. To add an item, set bits at positions h1(item)...hk(item). To query, check if all k bits are set. If any is zero: definitely not present. If all are one: probably present (false positive possible).

No deletions. No false negatives. Space efficiency is extreme: 10 bits per item yields ~1% FP rate. Chrome uses a 2MB Bloom for Safe Browsing (~1M URLs). We use 128 bits for ~30 agents at ~1.2% FP.

Tradeoff is intentional. We do not need perfect attribution, we need probabilistic contact history that cannot be forged without doing the work. Bloom filters are also mergeable via bitwise OR, perfect for combining nests when images are collaged.

Critically, they are deniable. You cannot prove an agent touched an image, only that it probably did, which protects researchers in hostile jurisdictions.

5. Merkle Bloom Hybrid

Merkle gives order. Bloom gives set. Neither alone solves provenance for mutable media.

Our hybrid stores both in 32 bytes (16+16). The Merkle root ensures linear history: you cannot reorder edits without breaking the chain. The Bloom filter ensures breadth: you can accumulate unlimited agents touching the same version without growing storage.

Construction: On creation, merkle_0 = H(blake3(IDAT) || 0x00), bloom_0 = 0. On each touch by agent A:

bloom_1 = bloom_0 OR bits(A)
leaf_1  = H(merkle_0 || bloom_1 || ts || geohash)
merkle_1 = merkle_root(merkle_0, leaf_1)

The nest stores only merkle_1, bloom_1, and prev_root=merkle_0. Verifier with access to prior PNG can recompute leaf_1 and check the link.

Why truncate to 128-bit roots? Collision resistance to 2^64 is sufficient for non-adversarial image history and saves 16 bytes. We use BLAKE3 because it's fast on ARM, stable across languages, and keyed.

Hybrid proofs are tiny: to prove an agent touched version 5 in a 1000-version history, you send 16-byte bloom, 16-byte root, plus ~160 bytes Merkle path. <200 bytes total, fits in QR.

This is what blockchains wanted to be before they became casinos: a way to commit to history without a network.

6. PNG Nesters (how we hide data after IEND)

PNG is a chunked format: 8-byte signature, then series of chunks: [length:4][type:4][data:length][crc:4]. The spec mandates that decoders stop after the IEND chunk (type 0x49454E44). Anything after is explicitly allowed and must be ignored.

This is not steganography. It is spec-compliant trailer data. The W3C PNG tests include files with trailing garbage; all browsers render them.

Advantages over ancillary chunks (tEXt, zTXt, iTXt): 1) CDNs strip ancillary chunks for "optimization". Cloudflare Polish, AWS Serverless Image Handler, and imgproxy all remove them. 2) Social networks re-encode and drop them. 3) They appear in metadata parsers.

Trailing data survives: Discord (as file, not proxy), Mastodon, Bluesky, Signal, Telegram, GitHub, S3, IPFS (as raw). It does NOT survive: X/Twitter, Facebook, Instagram, LinkedIn (they convert PNG→JPEG/WebP). Acceptable: lossy conversion is an edit, history breaks anyway.

00000000  89 50 4E 47 0D 0A 1A 0A  ...  │ PNG signature
... IDAT chunks ...
0001A340  00 00 00 00 49 45 4E 44  │ 00 00 len, "IEND"
0001A348  AE 42 60 82              │ IEND CRC ← decoder stops here
0001A34C  4E 45 53 54 01 08 03 10  │ NEST magic, ver, shells, k, m/8 ← our data starts
0001A354  ... 124 more bytes ...
0001A3D0  45 4E 44 4E              │ ENDN footer

Detection is O(1): seek to EOF-132, check magic. No PNG parse needed for verification.

We call this "nesting" because birds do not modify trees; they build after.

7. The Nest Format (132 bytes breakdown)

Version 1, little-endian unless noted. All multi-byte integers LE.

OffsetSizeFieldDescription
04magic0x4E455354 "NEST"
41ver0x01
51shells0x08 (eight shells)
61kBloom hashes (3)
71mBloom bytes (16)
816merkle_rootBLAKE3-128 of current tree
2416prev_rootPrevious root, 0 for genesis
4016bloom128-bit agent filter
5616work_hashPoW: H(header||nonce) with 20 lz bits
728timestampUnix ms, LE
808geohashlat/lon packed (see §9)
8810charge5× uint16: [t,s,soc,c,sem]
9816agent_fpLast writer fingerprint
1146ironIron Rain counter (48-bit)
1208ansibleNearest ansible vector (2× int32)
1284crc32CRC32 of bytes 0-127

Total: 132 bytes. Fits in a single Ethernet frame with overhead. Intentionally not 128 to avoid alignment with crypto block sizes.

Future versions may extend by appending NEST2 after first; parsers read last valid.

8. ((((((((1)))))))) — eight shells explained

The eight shells are concentric contexts, from pixel to planet. Reading inward costs more compute; most verifiers stop at Shell 3.

7 Core: blake3(IDAT). Pixel identity. Changes on any re-encode.

6 Microbe: Timestamp + PoW nonce. Proves when, not who.

5 Lichen: Geohash + city code (BUF/ROC/MSP). Ties to place, not GPS precision.

4 Mycelium: Bloom filter. Who touched.

3 Root: prev_root link. Parentage.

2 Trunk: merkle_root. Whole history commitment.

1 Canopy: Ansible coordinates. Where in semantic forest.

0 Atmosphere: Iron Rain counters, charge vector. How it moves through networks.

The nesting order matters: outer shells can be updated without recomputing inner expensive hashes. Iron Rain increments only touch bytes 114-119 + CRC.

Philosophically, this mirrors how we know a photo: first you see it circulate (Atmosphere), then where it lives online (Canopy), then its edits (Trunk), origin (Root), who shared it (Mycelium), where taken (Lichen), when (Microbe), and finally what pixels (Core). Most humans never get past Shell 4.

9. Iron Rain and charge vector [0,0,8,0,0]

Iron Rain is named for lake-effect snow in Buffalo: a sudden, heavy, uniform deposition that erases individual tracks.

Each nest carries a charge vector of five uint16s: [temporal, spatial, social, compute, semantic]. Genesis nests created by our tagger are initialized to [0,0,8,0,0] — eight units of spatial charge, zero elsewhere. Meaning: "this image is anchored to a place, not yet shared."

As the file moves:

  • Each unique ASN that serves it: +1 social, -1 spatial
  • Each day elapsed: +1 temporal
  • Each verification PoW: +1 compute
  • Each semantic tag added by agent: +1 semantic

When social ≥ 1000 and temporal ≤ 72h and spatial ≤ 2, the nest enters Iron Rain. The iron counter (bytes 114-119) increments. We flip the visual representation in readers to a desaturated preview: the image has become weather.

Why? To distinguish between a family photo (high spatial, low social) and a meme (low spatial, high social). Models should weight them differently. Teaching silicon about cities requires knowing which images are lived-in versus which are broadcast.

Charge is not consensus; it's local observation. Your node sees different values than mine. That's fine. Mycelium does not agree, it gradients.

10. Proof of Work without blockchain

To prevent a bot from flipping all 128 bits in a second, we require a small proof-of-work per touch. No chain, no difficulty adjustment, no reward.

Target: H(blake3, header[0:56] || nonce[8]) must have 20 leading zero bits (~1 in 1,048,576). On a 2023 laptop core, ~40-80ms. On a phone, ~200ms. Trivial for a human tagging 10 photos, expensive for a million.

The work_hash is stored in bytes 56-71. Verification is one hash. No network.

Unlike Bitcoin, work is not competitive; it's per-file and per-agent. Two agents can work in parallel, both valid, resulting in two sibling nests with same prev_root (a fork). Readers merge blooms via OR and pick higher iron count as canonical — eventual consistency, not consensus.

This is proof-of-effort, not proof-of-stake. It makes spam have a thermodynamic cost without creating currency. Archivists in Rochester running old ThinkPads can still participate; they just wait 0.3s.

def find_nonce(header):
    for nonce in range(2**64):
        h = blake3(header + nonce.to_bytes(8,'little')).digest()
        if int.from_bytes(h[:3],'big') >> 4 == 0: # 20 zero bits
            return nonce

11. The 4 Ansibles (-+8 0 0 0 8)

Ansibles are fixed reference points in the 5-dimensional charge space, named for Le Guin's instantaneous communicators. They allow decentralized spatial indexing without GPS or servers.

We defined four during Iron Rain winter 2024:

NameCoords [t,s,soc,c,sem]CityPurpose
A0 BUF[-8,0,0]Buffalo, NYTemporal west (past)
A1 ROC[+8,0,0]Rochester, NYTemporal east (future)
A2 MSP[0,0,0,0,-8]Minneapolis, MNSemantic south (concrete)
A3 DUL[0,0,0,0,+8]Duluth, MNSemantic north (abstract)

Any nest computes its Euclidean distance to each ansible after normalizing charge. The nearest two form a 2D coordinate stored in bytes 120-127. This gives rough clustering: Buffalo winter photos drift toward BUF+MSP; AI-generated cityscapes drift toward DUL+ROC.

Clients can query "show me images near BUF" by scanning local folders for nests with ansible distance < 3. No central index.

The coordinates -+8 are deliberate: they exceed maximum normal charge (which caps at 8 per axis), ensuring ansibles are always outside the data cloud, like lighthouses.

12. Teaching Silicon About Buffalo, Rochester, Minneapolis

0root.ai started not as a protocol but as a dataset. In 2023 we fine-tuned SDXL on 47,000 photos taken between 1978-2023 in three cities: Buffalo, Rochester, Minneapolis. All photos were scanned from the Lower Lakes Archive, city planning departments, and personal collections. None came from LA, London, or subsampled LAION.

The model initially failed. Asked for "winter street at dusk", it produced cinematic Tokyo neon. Asked for "porch in January", it gave California stucco. The latent space had no representation for: vinyl siding with ice dams, glass bus shelters fogged from -15°F breath, salt-stained Dodge Caravans, leaded glass at 4:17pm in December, the specific gray of lake-effect sky.

We realized the problem was not model size but provenance starvation. Internet-scale datasets treat these cities as noise. Their images are not tagged "Buffalo"; they're tagged "city", "snow", "USA". Captioners (BLIP, etc.) were trained on coasts, so they hallucinate palm trees.

Merkle Bloom was built to fix the data, not the model. Every image we scanned was PNG-nested at origin with geohash, timestamp from back of print, and initial charge [0,0,8,0,0]. As volunteers re-tagged, each agent flipped bits. As images spread to local history groups, iron counters rose.

After 6 months, we retrained with loss weighted by spatial charge (images that stayed local weighted higher). The model learned: Rochester has blue recycling bins, not green. Buffalo has angled parking downtown. Minneapolis skyways connect at second floor, not ground.

This is "teaching silicon about cities": not giving it more data, but giving it situated data with a memory of where it has been. A nest is a tiny syllabus.

We publish the weights as shareware (§14). Use them to generate your own streets, but you must nest your outputs. The cities taught the model; the model must remember.

13. How to Use (tagger, reader)

Reference implementation: Python 3.11+, no dependencies beyond blake3.

pip install blake3

# tag.py
import struct, time, blake3
from pathlib import Path

MAGIC = b'NEST'
def nest_png(path, agent_id, lat, lon):
    data = Path(path).read_bytes()
    iend = data.rfind(b'IEND') + 8
    # check existing
    if data[-132:-128] == MAGIC:
        prev = data[-132:-116]
    else:
        prev = b'\x00'*16
    merkle = blake3.blake3(data[:iend] + prev).digest()[:16]
    bloom = bytearray(16)
    for i in range(3):
        h = blake3.blake3(agent_id + merkle + bytes([i])).digest()
        idx = h[0] % 128
        bloom[idx//8] |= 1 << (idx%8)
    header = struct.pack('<4sBBBB', MAGIC,1,8,3,16) + merkle + prev + bytes(bloom)
    # ... add timestamp, geohash, pow etc.
    # simplified: append
    Path(path).write_bytes(data + header.ljust(132, b'\x00') + b'ENDN')

Reader (JavaScript, in-browser):

async function readNest(file) {
  const buf = await file.arrayBuffer();
  const view = new Uint8Array(buf);
  const tail = view.slice(-132);
  if (String.fromCharCode(...tail.slice(0,4)) !== 'NEST') return null;
  const dv = new DataView(tail.buffer);
  return {
    merkle: [...tail.slice(8,24)].map(b=>b.toString(16).padStart(2,'0')).join(''),
    bloomBits: [...tail.slice(40,56)].reduce((c,b)=>c+popcnt(b),0),
    timestamp: Number(dv.getBigUint64(72, true)),
    charge: Array.from({length:5},(_,i)=>dv.getUint16(88+i*2,true))
  };
}
